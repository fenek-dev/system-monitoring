### RSS growth (+115 MB in the first "background" run) — explained, not a leak
1. **Plateau, not linear.** Dashboard open 10 min (user on Overview): footprint 20 → 74 MB within the first minute, then
   71–79 MB for 9 minutes; RSS 142 → 147 MB. UI never opened: footprint 20–22 MB flat.
2. **Not returned after close.** Debug drill (dashboard open → CPU → minimize → Thermals → Processes → close):
   footprint 21 → 59–61 MB, 52 MB three minutes after close. At 75 s after close: live heap 16.5 MB (base 8.6 MB);
   MALLOC_SMALL **43 MB dirty** (base 15 MB) with only 1.7 MB reclaimable; graphics ~5 MB. So ~8 MB of live objects
   stay (one-time Swift type metadata +1.7 MB, ObjC method caches +0.6 MB, SwiftUI/AppKit internals, the model's last
   presented arrays ~0.6 MB) and ~25 MB is **malloc fragmentation** (freed small blocks on dirty pages).
   `malloc_zone_pressure_relief` on UI close released **0 KB** (tried in LivePipeline, reverted).
3. **Leaks:** `leaks` 192–288 objects / 9.6–14.5 KB, all Apple XPC cycles (`com.apple.linkd.autoShortcut`,
   AppIntents registration) — present at baseline, not ours.
4. **Top allocation sites with the dashboard open** (Release `heap`, 27 MB live of 76 MB footprint):
   - SwiftUI view graph / display lists / per-cell `.help()` tooltips and button styles (HelpStyleConfiguration ×1 962,
     PrimitiveButtonStyleConfiguration ×1 772, AnyTrackedValue dictionaries 0.7 MB) — **W5c/W3** (Processes table: a
     `.help` + button style per cell; ProcessListTable / TTTable).
   - Metal/IOSurface/IOAccelerator for window + layer backing: 20 MB footprint — AppKit/SwiftUI rendering (W4 window).
   - Engine state: RateCalculator dictionaries 0.7 MB, ProcessSample/AppSample arrays 0.8 MB (frame copies), disk-session
     baselines 0.2 MB, session accumulator 0.2 MB, sensor identity cache 0.16 MB (W1/W7/W6a) — bounded (pruned per tick).
   Proposals: W5c — drop per-cell `.help` (one tooltip per row, or on hover only) and plain-style buttons in table cells;
   W4 — tear down the dashboard `NSHostingView`/window on close (not just order out) so its graph and backing stores go.

assembly 0.8 %, coalitions 0.5 %, AGX clients 0.5 %, SMC 0.25 %, IOReport 0.2 %; `ps` (rootMemory) 0.7 %; NStat 0.4 %.
Top 3 hot paths / owners: (1) SwiftUI update of the Processes table per tick — **W5c/W3**; (2)
`ProcessTableModel.build` per tick — **W5c** (diff/sort only when rows change, sort once per frame); (3)
`ProcessTableBuilder.build` — **W6a**.

### assemble920 regression (3.7 ms vs 1.90) — attributed
Bisect (same machine load, release): w1-done 2.48 · 721ea9a (newborn) 2.34 · e5ef2de (ICR-13) 3.26 · b5d0c95 3.35 ·
HEAD 3.72. The ICR-13 step was the **benchmark data**: its 520 all-visible coalitions had coalition CPU ≫ Σ members, so
~500 "Exited processes" rows were created and measured. With realistic coalitions (Σ members + 1 %): **2.68 ms**.
Live profile of assembly: `AppGrouper.group` ≈ 25–30 % (sort tie-break by `String <` hit Unicode collation for ~500
apps at 0 %) → UTF-8 byte order (dc08b7e); ProcessAssembler ≈ 50 %; CoalitionAttributor ≈ 5 %; energy ≈ 4 %.
Recorded fixture (idle, 339 procs after trim): 1.66 ms mean (`telltale-probe --replay … --bench`).
