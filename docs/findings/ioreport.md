## ioreport — libIOReport
- Status: ✅ (M1 Max, macOS 26.5). Unprivileged, no root, no `sudo` needed for any of this.
- Energy channel names → metric (all in "Energy Model" group, values are accumulated energy since subscribe; convert to W via `raw / unitDivisor / dt`, unit divisors `{"mJ":1e3, "uJ":1e6, "nJ":1e9}`):
  - CPU: `CPU Energy` (mJ) = package-wide aggregate. Finer breakdown also present: `EACC_CPU`/`PACC0_CPU`/`PACC1_CPU` (per-cluster totals), `EACC_CPU0/1`, `PACC0_CPU0..3`, `PACC1_CPU0..3` (per-core), plus `EACC_CPM`/`PACC0_CPM`/`PACC1_CPM` (cluster uncore/interconnect) and a pile of `*DTL##` channels (finer per-die-location duplicates of the same clusters — redundant with the per-core ones above, ignorable).
  - GPU: two independent channels, both present — `GPU0` (mJ, + separate `GPU SRAM0`) and `GPU Energy` (nJ, a derived/summary channel). Same order of magnitude; either works.
  - ANE: `ANE0` (mJ). Present but read 0.000 W in every run here — `yes`-based CPU load never touches the Neural Engine and there's no easy no-root ANE trigger, so this is unverified beyond "the channel exists and parses".
  - DRAM: `DRAM0` (mJ).
  - Other Energy Model channels worth knowing about: `ISP0` (image signal processor), `AVE0` (Apple Video Encoder), `MSR0`, `DCS0` (memory-controller domain), `AMCC0` (SoC memory fabric). All non-zero even at idle (a few mW–a few W) — background media/display activity.
- Cluster/core channels (group `CPU Stats`):
  - Subgroup `CPU Complex Performance States`: one channel per cluster — `ECPU`, `PCPU`, `PCPU1` — plus a paired `ECPM`/`PCPM`/`PCPM1` channel each. The `*CPM` channels are NOT the same thing as the plain cluster channels: they use combined voltage+perf-state names (`V0P14`, `V1P13`, … down to `V14P0`) instead of plain `P1..P15`, and read ~100% "active" almost regardless of real load (their literal `IDLE` state residency stayed at 0 in every run) — looks like a "powered vs. fully-off" tracker rather than a duty-cycle-at-frequency tracker. Use the plain `ECPU`/`PCPU`/`PCPU1` channels for real P-state residency.
  - Subgroup `CPU Core Performance States`: one channel per physical core — `ECPU000`, `ECPU010` (2 E-cores), `PCPU000..030` (P-cluster 0, 4 cores), `PCPU100..130` (P-cluster 1, 4 cores) — confirms the expected 2+4+4 = 10-core M1 Max topology directly from channel names, no other API needed.
  - GPU channel (group `GPU Stats`, subgroup `GPU Performance States`): a single channel `GPUPH` with 16 states: `OFF`, `P1`..`P15`. Contrary to the design doc's guess, these are **not** literal MHz names — they're anonymous indices, same style as the CPU ones.
  - Idle/off state names actually seen: both `IDLE` and `OFF` occur (which one, depends on the channel — CPU-core/cluster/GPU channels use `OFF`, the `*CPM` channels use `IDLE`). `DOWN` never appeared on this chip; the brief's 3-name set `{"IDLE","OFF","DOWN"}` is a safe superset.
- Full channel/group discovery (EXTRA):
  - `IOReportCopyChannelsInGroup(nil, nil, 0, 0, 0)` returns **nil** in practice — `group` is effectively required, despite the header typing it as an ordinary (nilable-looking) `CFStringRef`. Found `IOReportCopyAllChannels(a, b)` via `nm -gU libIOReport.tbd` and added it to our `IOReport.h` (not in the brief's snippet); called as `IOReportCopyAllChannels(0, 0)` it does list everything.
  - Result: **956 unique (group, subgroup) pairs, 9505 channels total** on this machine.
  - No separate top-level "ANE" or media-engine ("AVE"/"VDEC"/"ProRes") group exists — `ANE0`, `AVE0`, `ISP0`, `MSR0`, `DCS0`, `AMCC0` are just individual channel names folded into the single `Energy Model` group. `PMP` shows up only as a *subgroup* under various groups (frequency-floor/voting diagnostics like `PMP/AF BW`, `PMP/DCS Floor`, `PMP/SOC0_ANE_SYS Fl`), not as its own energy/residency source.
- P-state → MHz (EXTRA, no root): source is IORegistry `pmgr` node, `ioreg -l -w0 -c AppleARMIODevice -n pmgr`, keys `voltage-states<N>[-sram]`. Format (reverse-engineered, confirmed against known M1 Max spec numbers): each entry is 8 bytes = `UInt32` LE frequency-in-Hz followed by `UInt32` LE voltage-in-mV, repeated.
  - `voltage-states1-sram` = ECPU table: `[600, 972, 1332, 1704, 2064]` MHz (5 states) — count+1 (idle) = 6, matches the `ECPU`/`ECPU000`/`ECPU010` channels' 6 states exactly.
  - `voltage-states5-sram` = PCPU table (shared by both P-clusters): `[600, 828, 1056, 1296, 1524, 1752, 1980, 2208, 2448, 2676, 2904, 3036, 3132, 3168, 3228]` MHz (15 states) — count+1 = 16, matches `PCPU`/`PCPU1`/all 8 per-core P channels exactly.
  - `voltage-states9` = GPU table: `[0, 388, 486, 648, 777, 972, 1296]` MHz (7 states) — does **not** line up with `GPUPH`'s 16 states (OFF+P1..P15). GPU frequency-from-residency is therefore **not implemented/trustworthy** here; the SoC's GPU DVFS apparently exposes finer interpolated states than the 7 physical voltage points in `pmgr`. Left as residency-only for GPU, matching the brief's own fallback.
  - These `voltage-states*` → domain mappings (1-sram/5-sram/9) were found empirically by decoding every key and matching frequency ranges to known M1 Max numbers; they are undocumented, chip-generation-specific, and will need to be re-derived on M2/M3/M4 Macs.
  - Where it worked (all CPU channels), the computed weighted-average active frequency tracked load sensibly (see plausibility run below) — e.g. idle E-cluster ~1555 MHz avg climbing to 2064 MHz (its max) under load, P-clusters ~2080 MHz avg climbing to 3228 MHz (max) under saturation. Treat as directionally correct but **not validated against powermetrics' own frequency algorithm** (no sudo in this environment) — could be biased by race-to-max behavior.
- Sample cost: `IOReportCreateSamples()` on our 179-channel subscription (Energy Model + CPU Complex + CPU Core + GPU Performance States), measured over 5 back-to-back calls with `ContinuousClock`: **min 1.68 ms / avg 1.85 ms / max 2.13 ms**. Cheap — fine for a 1 Hz or even 10 Hz UI poll.
- Accuracy vs `powermetrics`: **not directly checked** — `sudo powermetrics` needs an interactive TTY password not available to the agent in this environment (per task instructions, the user was to run it themselves; no confirmation was provided back). Did a plausibility check instead:
  - Idle (best-effort quiet moment — `ps` showed only WindowServer, `bird`, and the usual Claude/Discord helper renderers, nothing unusual): `CPU Energy` = **2.254 W**. This is in the right ballpark for the stated "0.1–3 W idle" expectation, on the high side because this dev machine is never fully quiescent (browser + chat app renderers running).
  - Load — `for i in $(seq 8); do yes >/dev/null & done`, sampled ~1s later, then `killall yes`: `CPU Energy` = **8.050 W** (+5.8 W, "several watts" as expected). Both P-clusters (`PCPU`, `PCPU1`, and all 8 per-core P channels) pinned to **100% active at their max table frequency (3228 MHz)**; the E-cluster rose from 64%→82% active and 1555→2064 MHz avg. `GPU Energy` moved the *other* way (1.23 W → 0.79 W), which makes sense since `yes` never touches the GPU — a good cross-check that these are independent per-domain counters, not one shared noisy number.
  - Caveat: this machine runs other concurrent work (other spikes, builds). An earlier attempt at the same idle/load pair caught a concurrent `clang`/`swift-frontend` build saturating both P-clusters during the "idle" sample (`CPU Energy` = 10.3 W, clusters already 100% active) which barely moved after adding `yes` — i.e. the *comparative* idle→load story only holds when nothing else heavy is running; treat single readings as noisy on a shared dev box, not as absolute idle-power ground truth.
- Gotchas:
  - `IOReportCopyChannelsInGroup(nil, nil, 0, 0, 0)` returns `nil` — use `IOReportCopyAllChannels(0, 0)` (added to `IOReport.h`, not in the original snippet) for full discovery instead.
  - `*CPM` cluster channels and the GPU `GPUPH` channel use non-obvious state-name schemes (`V#P#` combined codes; anonymous `P1..P15` with no MHz in the name) — don't assume state names are self-describing.
  - The `pmgr` `voltage-states*` key→domain mapping is reverse-engineered per-chip, not a stable API; re-derive per SoC generation before trusting it in product code.
  - `POSIXErrorCode` gotcha from Task 1 (`POSIXErrorCode` doesn't conform to `Error`, use `POSIXError`) didn't come up here — libIOReport failures surface as `nil` pointers, not `errno`/POSIX errors.
