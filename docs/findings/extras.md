# M0 Findings (M1 Max, macOS 26.5)

## extras — disk IOPS, NVMe SMART, sleep assertions, router ping, Wi-Fi

### 1. Disk IOPS/bytes — `IOServiceMatching("IOBlockStorageDriver")` + `Statistics`
- Status: ✅
- Cost: two samples 1s apart, each sample (enumerate + read `Statistics` on every driver) costs 0.06–0.63 ms. The 1s is just the intentional sleep between samples, not API overhead.
- Keys: `Operations (Read)`, `Operations (Write)`, `Bytes (Read)`, `Bytes (Write)` inside the `Statistics` CFDictionary property on each `IOBlockStorageDriver` service.
- This run found 6 drivers: the internal SSD (`disk0`, delta over 1s: ~5 readIOPS / ~200 writeIOPS / 1.15 MB/s write, background system activity), 4 `Apple Disk Image Media`-backed drivers (all idle, mounted disk images), and one driver with **no child media at all** (an `IOBlockStorageDriver` matched with `device-type=Generic` but nothing attached under it — confirmed via `ioreg -c IOBlockStorageDriver -r -d 2`).
- Naming the media: the brief says "name the *parent* media BSD name", but the actual registry shape is the other way around — `IOMedia` (which carries `BSD Name`) is a **child** of `IOBlockStorageDriver`, not a parent. Walking `IORegistryEntryGetChildIterator` and taking the first child with a `BSD Name` property works and resolved `disk0` for the internal SSD. The one driver with no media child correctly shows up as `[?]` — that's a real "unreachable" case, not a bug.
- No permission issues; no root needed.

### 2. NVMe SMART — `NVMeSMARTLibExternal.h` CFPlugIn
- Status: ⚠️ partial — plugin creation and interface query both succeed, but `SMARTReadData` fails.
- Cost: registry-walk lookup of the SMART-capable service ≈ 11 ms (a full `IOServiceMatching(kIOServiceClass)` sweep of the whole registry, since Apple Silicon has no `IONVMeController` class to match on — see below); `SMARTReadData` call itself ≈ 3–6 ms (fails fast).
- Keys: would be `PERCENTAGE_USED`, `DATA_UNITS_READ[0]`/`DATA_UNITS_WRITTEN[0]` (×512000 = bytes), `POWER_ON_HOURS[0]`, `UNSAFE_SHUTDOWNS[0]`, `TEMPERATURE` (Kelvin), `CRITICAL_WARNING` — all wired up in the C helper (`Spikes/Sources/CPrivate/nvme_smart.c`) and printed by the spike, but none of it is populated because the read never succeeds.
- **Finding: `IOServiceMatching("IONVMeController")` matches nothing on this Apple Silicon Mac.** The registry walk (confirmed with `ioreg -l`) shows the internal SSD is `AppleANS3CGv2Controller` → `NS_01@1` of class **`IOEmbeddedNVMeBlockDevice`**, and it's *that* node that carries `"NVMe SMART Capable" = Yes` and `"IOCFPlugInTypes" = {"AA0FA6F9-...": "NVMeSMARTLib.plugin"}`, several levels below anything named `IONVMeController`. The spike does a flat `IOServiceGetMatchingServices(kIOMainPortDefault, IOServiceMatching(kIOServiceClass), …)` sweep and filters by the `NVMe SMART Capable` property directly, per the brief's fallback option — that's the only thing that found it.
- `IOCreatePlugInInterfaceForService` and `QueryInterface(kIONVMeSMARTInterfaceID)` both return success — the plugin infrastructure and the vtable are there. `SMARTReadData` fails with `IOReturn = 268435459` (`0x10000003`), which `mach_error_string()` decodes as **`(ipc/send) invalid destination port`**. This is not an `EPERM`/root issue — no permission prompt or root re-run would fix it — it looks like Apple's Fabric/ANS3-based internal SSD registers the standard `NVMeSMARTLib` plugin type (so third-party code correctly finds a "SMART capable" NVMe device and can open a connection) but the backing user client either doesn't implement the external method `SMARTReadData` dispatches to, or the connection is torn down/invalid by the time the call reaches it. This matches the widely-reported real-world limitation that generic NVMe SMART tools (e.g. `smartctl`) do not get SMART data from Apple Silicon's *internal* SSD, and only work against genuine third-party NVMe controllers (e.g. an external Thunderbolt/USB NVMe enclosure) — untested here since no such device was attached.
- Not verified as root (no interactive `sudo` in this environment) — but the specific `mach_error_string` returned is not one that reads as a privilege/entitlement failure, so root is unlikely to change the outcome. Flagging as a concern for whoever scopes M1+.

### 3. Sleep assertions — `IOPMCopyAssertionsByProcess`
- Status: ✅
- Cost: 0.67–0.85 ms for the whole call (single Mach IPC round trip, no root needed).
- Keys: top-level dict is `[pid: CFNumber → [assertion CFDictionary]]`; each assertion dict read via `"AssertType"` (`kIOPMAssertionTypeKey`) and `"AssertName"` (`kIOPMAssertionNameKey`).
- Real assertions observed on this machine at run time: `powerd` (pid 359) holding `PreventUserIdleSystemSleep` ("Powerd - Prevent sleep while display is on"); `coreaudiod`-style pid 440 holding 2-3 `PreventUserIdleSystemSleep` assertions tied to specific audio device output contexts; `WindowServer`-adjacent pid 418 holding a `UserIsActive` assertion tied to trackpad/keyboard HID tickles; Arc (pid 98386) and Claude desktop (pid 55507) each holding a `NoIdleSleepAssertion` (audio playback / Electron). `PreventUserIdleDisplaySleep` was 0 in every run (no app was actively blocking display sleep at the time).
- Gotcha: `proc_name()` fails (falls back to `"pid N"`) for pids owned by other users/root (`powerd` 359, `WindowServer` 418) — same EPERM-style gating documented in task 1's procs spike, so pid→name resolution for system daemons needs another source (e.g. a lookup table or `launchctl`) if display names matter later.

### 4. Router latency and loss — gateway discovery + unprivileged ICMP
- Status: ✅ (after one real bug found and fixed)
- Cost: `sysctl(NET_RT_FLAGS, RTF_GATEWAY)` gateway lookup ≈ 0.06–0.13 ms; `SCDynamicStore` lookup ≈ 0.4–0.8 ms; both agreed on `192.168.1.1` every run, so the sysctl path (preferred per the brief) is both correct and ~5x cheaper. The `route -n get default` shell-out fallback was never needed. 5 pings 200ms apart cost ≈ 830 ms total end-to-end (dominated by the 4×200ms inter-ping delay + RTT), loss 0%, RTT min/avg/max ≈ 2.46/3.32/5.97 ms (comparable to plain `ping -c 3 192.168.1.1`, which measured 2.5–3.4 ms RTT on this network).
- Implemented the `sysctl(CTL_NET, PF_ROUTE, 0, AF_INET, NET_RT_FLAGS, RTF_GATEWAY)` routing-socket-message parse manually (walking `rt_msghdr` + `RTAX_*`-indexed `sockaddr`s, rounding each to `sizeof(long)`/8 bytes per BSD's `ROUNDUP` convention, zero-padding truncated `sockaddr_in`s for the "any" `0.0.0.0` destination). It matched `SCDynamicStore`'s answer on every run, so the "prefer sysctl" guidance in the brief holds up as more than just theoretically viable.
- **Real bug found and fixed**: `socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)` on macOS delivers replies **with the IPv4 header still attached** (20 bytes, `recvBuf[0] == 0x45`), unlike a UDP datagram socket which strips it. The first version of the spike read the ICMP type/id/seq straight from byte 0 and got 100% loss (it was actually parsing the *IP header's* version/IHL/identification/flags fields as if they were ICMP type/id/seq). Diagnosed by comparing against a passing `ping -c 3 192.168.1.1` and instrumenting the raw received bytes. Fix: skip `(recvBuf[0] & 0x0f) * 4` bytes (the IP header, using its own IHL field rather than assuming exactly 20) before reading the ICMP header. After the fix, identifier/sequence matching against our own sent packet worked with no further surprises — no evidence the kernel rewrites the ICMP identifier field on send for this socket type.
- No root/entitlement needed; unprivileged ICMP-over-DGRAM confirmed working as documented.

### 5. Wi-Fi — `CoreWLAN`
- Status: ✅ (with the documented SSID gap)
- Cost: `CWWiFiClient.shared().interface()` ≈ 3–40 ms (first call in a run is the expensive one, ~40ms cold, ~3ms after; consistent with lazy-loading the CoreWLAN daemon connection XPC/IPC).
- Keys: `rssiValue()`, `noiseMeasurement()`, `transmitRate()`, `ssid()`, `wlanChannel()` → `channelNumber`/`channelBand`/`channelWidth`, all read successfully as plain method calls on the `CWInterface` (imported into Swift as no-arg methods, not properties).
- Real values this run: `en0`, RSSI -64 to -67 dBm, noise -89 dBm, transmit rate 292–390 Mbps (fluctuates between runs), channel 52 / 5GHz / 80MHz.
- `ssid()` returned `nil` on every run, exactly as the brief predicted — this process has no Location permission entitlement, and CoreWLAN gates SSID (and BSSID) behind it since macOS 10.15. This will need a real app bundle with `NSLocationUsageDescription`/entitlement + user consent (or reading the SSID from `SCDynamicStore`'s `State:/Network/Interface/en0/AirPort` instead, which is not gated the same way) if the shipped app wants to show SSID.
- `import CoreWLAN` auto-linked cleanly with no `Package.swift` changes needed, as expected for a public system framework.

## Cross-cutting notes
- No `Package.swift` edits were needed. `import CoreWLAN` and `import SystemConfiguration` both auto-link as public system frameworks; only `CPrivate` needed a new file pair (`nvme_smart.c` / `include/NVMeSMART.h`), which SwiftPM picked up automatically since the target has no explicit `sources:`/header list.
- All 5 items ran unprivileged, no root and no entitlements beyond the default debug `get-task-allow` SwiftPM already adds. The only "requires more than this spike has" item is NVMe SMART (see above) — and that's an IPC/user-client-implementation gap on Apple Silicon's internal SSD, not a privilege gap.
