# M0 Findings (M1 Max, macOS 26.5)

## extras — disk IOPS, NVMe SMART, sleep assertions, router ping, Wi-Fi

### 1. Disk IOPS/bytes — `IOServiceMatching("IOBlockStorageDriver")` + `Statistics`
- Status: ✅
- Cost: two samples ~1.01s apart (measured, not assumed), each sample (enumerate + read `Statistics` on every driver) costs 0.17–0.63 ms.
- Keys: `Operations (Read)`, `Operations (Write)`, `Bytes (Read)`, `Bytes (Write)` inside the `Statistics` CFDictionary property on each `IOBlockStorageDriver` service.
- This run found 6 drivers: the internal SSD (`disk0`, real delta over the measured interval: ~19000 writeIOPS / ~608 MiB/s write during an active build — background system activity from this very spike run compiling/linking), 4 `Apple Disk Image Media`-backed drivers (all idle, mounted disk images), and one driver with **no child media at all** (an `IOBlockStorageDriver` matched with `device-type=Generic` but nothing attached under it — confirmed via `ioreg -c IOBlockStorageDriver -r -d 2`).
- Rates are computed against the **actually-measured** elapsed wall time between the two samples, not an assumed 1.0s (the sleep call plus the two measurement passes add a few ms of jitter). Labeled `MiBps` (mebibytes, ÷1,048,576), not `MBps` — the divisor was already binary, only the label was wrong.
- Naming the media: the brief says "name the *parent* media BSD name", but the actual registry shape is the other way around — `IOMedia` (which carries `BSD Name`) is a **child** of `IOBlockStorageDriver`, not a parent. Walking `IORegistryEntryGetChildIterator` and taking the first child with a `BSD Name` property works and resolved `disk0` for the internal SSD. The one driver with no media child correctly shows up as `[?]` — that's a real "unreachable" case, not a bug.
- No permission issues; no root needed.

### 2. NVMe SMART — `NVMeSMARTLibExternal.h` CFPlugIn
- Status: ✅ (after fixing a real ordering bug — see below)
- Cost: targeted lookup via the BSD disk's parent chain (`disk0` → `IOMedia` → `IOBlockStorageDriver` → `IOEmbeddedNVMeBlockDevice`, the same approach smartctl uses) ≈ **0.6 ms**; `SMARTReadData` itself ≈ 2–3 ms. The original full-registry sweep (`IOServiceMatching(kIOServiceClass)` + filter on every service) is kept as a fallback if the parent-chain walk finds nothing, and costs ~11 ms when it has to run — ~18x more expensive, and it isn't needed on this machine.
- Keys: `PERCENTAGE_USED`, `DATA_UNITS_READ[0]`/`DATA_UNITS_WRITTEN[0]` (×512000 = bytes), `POWER_ON_HOURS[0]`, `UNSAFE_SHUTDOWNS[0]`, `TEMPERATURE` (Kelvin), `CRITICAL_WARNING`.
- **Critical bug found and fixed**: the first version of `Spikes/Sources/CPrivate/nvme_smart.c` called `IODestroyPlugInInterface(plugin)` right after `QueryInterface` succeeded, *before* calling `SMARTReadData` on the interface obtained from it. That tears down the user client's Mach connection before the actual SMART read's IPC call reaches it, so `SMARTReadData` always failed with `IOReturn = 0x10000003`, which `mach_error_string()` decodes as `(ipc/send) invalid destination port` — a red herring that looked like a capability gap in Apple's internal SSD controller, but was actually just this file destroying the plugin one call too early. Fix (matches smartmontools' `os_darwin.cpp` ordering): keep the plugin alive for the interface's whole lifetime, and only call `IODestroyPlugInInterface` *after* `(*smart)->Release(smart)`, on every return path.
- After the fix, `SMARTReadData` succeeds on the first try. Real values from this run, cross-checked against `smartctl -a disk0` (`smartctl` 7.2, installed via Homebrew, works fine unprivileged on this internal SSD — an earlier version of this doc wrongly claimed generic NVMe SMART tools don't work on Apple Silicon's internal SSD; that claim is retracted):

  | Field | This spike | `smartctl -a disk0` |
  |---|---|---|
  | Percentage used | 4% | 4% |
  | Temperature | 42.9–44.9°C (316–318K, varies run to run) | 39°C |
  | Power-on hours | 4693 | 4,693 |
  | Unsafe shutdowns | 25 | 25 |
  | Data units read | 236,717,362 units (×512000 ≈ 121.2 TB) | 236,717,213 units (≈121 TB) |
  | Data units written | 313,746,071–313,790,800 units (≈160.6 TB) | 313,699,098 units (≈160 TB) |

  Power-on hours and unsafe shutdowns match exactly. Data units read/written and temperature differ by small, live-counter-consistent amounts (the two tools ran seconds apart, and this spike's own build+link+I/O activity plausibly explains both the higher data-units-written delta and the higher temperature reading).
- `IOServiceMatching("IONVMeController")` still matches nothing on this Apple Silicon Mac (kept as a documented fact, not a workaround needed anymore now that the parent-chain lookup starts from the BSD disk instead): the registry walk (confirmed with `ioreg -l`) shows the internal SSD is `AppleANS3CGv2Controller` → `NS_01@1` of class `IOEmbeddedNVMeBlockDevice`, and it's *that* node that carries `"NVMe SMART Capable" = Yes` and `"IOCFPlugInTypes" = {"AA0FA6F9-...": "NVMeSMARTLib.plugin"}` — several levels below anything named `IONVMeController`, and reached directly by walking up from `disk0`'s `IOMedia` node.
- Not tested against an external Thunderbolt/USB NVMe enclosure (none attached) or as root (no interactive `sudo` in this environment) — neither was needed to get real data out of the internal SSD.

### 3. Sleep assertions — `IOPMCopyAssertionsByProcess`
- Status: ✅
- Cost: 0.47–0.85 ms for the whole call (single Mach IPC round trip, no root needed).
- Keys: top-level dict is `[pid: CFNumber → [assertion CFDictionary]]`; each assertion dict read via `"AssertType"` (`kIOPMAssertionTypeKey`) and `"AssertName"` (`kIOPMAssertionNameKey`).
- **Bug found and fixed**: `IOPMLib.h` documents `"NoIdleSleepAssertion"`/`"NoDisplaySleepAssertion"` as the legacy assertion-type names for the exact same functional assertion as `"PreventUserIdleSystemSleep"`/`"PreventUserIdleDisplaySleep"` (its own doc comment says "please use ... instead"). Several real, currently-running apps (Arc, Claude desktop, ChatGPT) still create assertions under the legacy name, so the first version of this spike — which only matched the literal new-style strings — undercounted `PreventUserIdleSystemSleep` (4 instead of the real 7). Fixed by normalizing both names onto the canonical one before counting, while still printing the original string in the per-process detail.
- Real assertions observed on this run, with process identities **verified via `ps -p <pid> -o pid,ppid,user,comm`** (not guessed from the assertion string text):
  - pid 359 → confirmed `powerd` (`/System/Library/CoreServices/powerd.bundle/powerd`), holding `PreventUserIdleSystemSleep` ("Powerd - Prevent sleep while display is on").
  - pid 440 → confirmed `coreaudiod` (`/usr/sbin/coreaudiod`, user `_coreaudiod`), holding 2–3 `PreventUserIdleSystemSleep` assertions tied to specific audio output device contexts.
  - pid 418 → confirmed `WindowServer` (`/System/Library/PrivateFrameworks/SkyLight.framework/Resources/WindowServer`, user `_windowserver`), holding a `UserIsActive` assertion tied to trackpad/keyboard HID tickle events.
  - Arc, Claude desktop, and ChatGPT (pids resolved directly by `proc_name()`, no guessing needed since they run as the current user) each hold a legacy-named `NoIdleSleepAssertion` (audio playback / Electron apps).
  - `PreventUserIdleDisplaySleep` (incl. legacy `NoDisplaySleepAssertion`) was 0 in every run — no app was actively blocking display sleep at the time.
- Gotcha: `proc_name()` fails (falls back to `"pid N"`) for pids owned by other users/root (`powerd`, `WindowServer`, `coreaudiod`) — same EPERM-style gating documented in task 1's procs spike — which is exactly why those three needed independent `ps` verification instead of trusting the spike's own output.

### 4. Router latency and loss — gateway discovery + unprivileged ICMP
- Status: ✅ (after two real bugs found and fixed)
- Cost: `sysctl(NET_RT_FLAGS, RTF_GATEWAY)` gateway lookup ≈ 0.06–0.13 ms; `SCDynamicStore` lookup ≈ 0.2–0.8 ms; both agreed on `192.168.1.1` every run, so the sysctl path (preferred per the brief) is both correct and ~2-5x cheaper. The `route -n get default` shell-out fallback was never needed. 5 pings, a fixed 200ms apart, cost ≈ 1.8s total end-to-end (4×200ms scheduled gaps + a 1s grace period after the last request), loss 0%, RTT min/avg/max ≈ 2.46/2.95/3.39 ms (matches plain `ping -c 3 192.168.1.1`, which measured 2.5–3.4 ms RTT on this network).
- **Bug found and fixed — wrong sockaddr alignment.** The routing-socket-message parse (`sysctl(CTL_NET, PF_ROUTE, 0, AF_INET, NET_RT_FLAGS, RTF_GATEWAY)`, walking `rt_msghdr` + `RTAX_*`-indexed `sockaddr`s) originally rounded each sockaddr up to `sizeof(long)`/8 bytes, following the traditional BSD `ROUNDUP` convention. That's wrong on Darwin: XNU's routing-socket message builder (`rtsock.c`) pads to a fixed 4-byte (`uint32_t`) boundary (`ROUNDUP32`) regardless of the reading process's native word size, so the kernel's wire format stays identical for 32-bit and 64-bit consumers. Verified empirically with a full `NET_RT_DUMP` (not just the `RTF_GATEWAY`-filtered set): a directly-connected/cloned route whose `RTAX_GATEWAY` is a 20-byte `sockaddr_dl` (a MAC address, not an IP) is followed by a `RTAX_NETMASK` field. Under 8-byte rounding, the extra 4 bytes of padding shift the read into the wrong position, and it silently decodes as a plausible-but-wrong `sockaddr_in` (`192.168.64.1`, coincidentally a real host elsewhere on this machine's routing table) instead of the expected zero-family netmask blob. Under 4-byte rounding it re-syncs correctly. Across the full local routing table (67 entries), 8-byte rounding produced 7x more end-of-message boundary overshoots (14) than 4-byte rounding (2) — strong, reproducible confirmation. Fixed by rounding to 4 bytes everywhere in the parse.
- **Bug found and fixed — reply IP header, not stripped.** `socket(AF_INET, SOCK_DGRAM, IPPROTO_ICMP)` on macOS delivers replies **with the IPv4 header still attached** (20+ bytes, `recvBuf[0] == 0x45`), unlike a UDP datagram socket which strips it. The first version of the spike read the ICMP type/id/seq straight from byte 0 and got 100% loss (it was actually parsing the *IP header's* version/IHL/identification/flags fields as if they were ICMP type/id/seq). Diagnosed by comparing against a passing `ping -c 3 192.168.1.1` and instrumenting the raw received bytes. Fix: skip `(recvBuf[0] & 0x0f) * 4` bytes (the IP header, using its own IHL field rather than assuming exactly 20) before reading the ICMP header.
- **Reply source-address verification added.** Every accepted reply is now checked against the gateway's actual `sockaddr_in` (via `recvfrom`'s `from` out-parameter), not just identifier+sequence — a stray or spoofed ICMP echo reply from an unrelated host on the wire, matching only by coincidence on id/seq, is rejected rather than counted as "the gateway answered".
- **Fixed 200ms send cadence, decoupled from reply timing.** The first version waited for each reply (up to its own timeout) before sleeping 200ms and sending the next request, so the real inter-request gap depended on how long each reply took, not a fixed period. Rewritten to send on an absolute schedule (`t = seq × 200ms` since the first send) and, after each send, block via `poll` only until either a reply arrives (RTT stamped the instant it's read) or the next scheduled send is due, whichever comes first — a plain non-blocking peek here was tried first and it "noticed" replies late (up to a full 200ms late), inflating measured RTT to ~160ms average while still reporting correct loss/received counts; blocking with a bounded budget both keeps the send schedule exact and keeps RTT accurate.
- **Known limitation, not exercised here**: this machine's own routing table already has two routes claiming destination `0.0.0.0` (`netstat -rn -f inet` shows `default via 192.168.1.1 (en0)` *and* `default via link#24 (bridge100)`, the latter from Docker's bridge network) — but only the first carries `RTF_GATEWAY`, so the `NET_RT_FLAGS`/`RTF_GATEWAY` filter already excludes the second and no ambiguity was hit. A VPN (`utun`) client that installs a *second* `RTF_GATEWAY` default route would not be filtered out this way, and this spike takes the first sysctl match with no metric/scope/interface tie-breaking — flagged in the spike's own output when `defaultGatewaysViaSysctl()` returns more than one candidate. A real implementation should prefer the interface named by `SCDynamicStore`'s `State:/Network/Global/IPv4` `PrimaryInterface`, or compare `rtm_rmx` route metrics, rather than taking the first match.
- No root/entitlement needed; unprivileged ICMP-over-DGRAM confirmed working as documented.

### 5. Wi-Fi — `CoreWLAN`
- Status: ✅ (with the documented SSID gap)
- Cost: `CWWiFiClient.shared().interface()` ≈ 3–40 ms (first call in a run is the expensive one, ~40ms cold, ~3ms after; consistent with lazy-loading the CoreWLAN daemon connection XPC/IPC).
- Keys: `rssiValue()`, `noiseMeasurement()`, `transmitRate()`, `ssid()`, `wlanChannel()` → `channelNumber`/`channelBand`/`channelWidth`, all read successfully as plain method calls on the `CWInterface` (imported into Swift as no-arg methods, not properties).
- Real values this run: `en0`, RSSI -58 to -67 dBm, noise -89 dBm, transmit rate 292–390 Mbps (fluctuates between runs), channel 52 / 5GHz / 80MHz.
- `ssid()` returned `nil` on every run, exactly as the brief predicted — this process has no Location permission entitlement, and CoreWLAN gates SSID (and BSSID) behind it since macOS 10.15.
- **Correction**: an earlier version of this doc claimed `SCDynamicStore`'s `State:/Network/Interface/en0/AirPort` SSID "is not gated the same way" as a workaround. That's false — verified directly with `scutil <<< 'show State:/Network/Interface/en0/AirPort'`, which shows `SSID_STR :` empty and `SSID : <data> 0x00` (a single redacted zero byte) on this same unprivileged process, i.e. `SCDynamicStore` is gated behind Location permission exactly like `CWInterface.ssid()`. There is no unprivileged escape hatch found so far; a real app will need `NSLocationUsageDescription` + the location entitlement + user consent to show SSID.
- `import CoreWLAN` auto-linked cleanly with no `Package.swift` changes needed, as expected for a public system framework.

## Cross-cutting notes
- No `Package.swift` edits were needed. `import CoreWLAN` and `import SystemConfiguration` both auto-link as public system frameworks; only `CPrivate` needed a new file pair (`nvme_smart.c` / `include/NVMeSMART.h`), which SwiftPM picked up automatically since the target has no explicit `sources:`/header list.
- All 5 items ran unprivileged, no root and no entitlements beyond the default debug `get-task-allow` SwiftPM already adds, and all 5 now report real, verified data (SMART needed a same-file ordering fix; nothing here needs root).
- Fix round 1 (this revision) corrected one critical bug (NVMe SMART plugin lifetime ordering), three correctness bugs (assertion-alias undercounting, sockaddr rounding, false SSID claim), and addressed several precision/verification gaps (measured vs. assumed elapsed time, MiB vs MB labeling, targeted vs. brute-force SMART service lookup, ping reply source verification, fixed send cadence, unverified process names, VPN/scoped-route limitation) flagged by review.
