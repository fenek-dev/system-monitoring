# M0 Findings (M1 Max, macOS 26.5)

## procs — proc_pid_rusage + responsible PID
- Status: ✅
- PIDs ok / EPERM / other: 591 / 330 / 0
- Denied notable: kernel_task (pid 0), launchd (pid 1), WindowServer (pid 418), mds_stores (pids 534, 45418) — all confirmed EPERM as expected (unprivileged, no root). Also root-owned daemons (XProtectPluginService, softwareupdated, PerfPowerServices, powermetrics, login, netbiosd, diskimagesiod, etc.) and other-user processes (`_nsurlsessiond`, `_softwareupdate`, `nobody`).
- Sweep cost (N pids, ~921 total): 2.12 ms (`sweep=0.002117625 seconds`)
- Energy (top consumers, W, from a representative 2.007s-window run): Telegram ≈ 0.0116 W, Claude Helper ≈ 0.0037 W, Browser Helper ≈ 0.0035 W, iStat Menus Menubar ≈ 0.0006 W, Discord Helper ≈ 0.0006 W. Sum across every non-EPERM'd pid this run ≈ 0.021 W total.
  - Units check: `ri_billed_energy` is documented in **nanojoules (nJ)**, so `W = Δ(nJ) / (dt · 1e9)` — exactly the formula `main.swift` uses (`g.watts += Double(b.energyNj &- a.energyNj) / (dt * 1e9)`). Dimensionally correct: nJ × 1e-9 = J, J / s = W.
  - Plausibility vs. typical Apple Silicon idle package power (~0.5–3 W total): our summed ~0.021 W is 25–150x lower. That's expected, not a bug — `ri_billed_energy` is a per-task *billed CPU/GPU* energy metric, not whole-SoC package power; it excludes display, radios, unattributed kernel/DVFS overhead, and — same gap as CPU above — the biggest real consumers this run (WindowServer, kernel_task, PerfPowerServices) are EPERM-denied and contribute nothing to our total. So the metric structurally under-counts total system power, independent of privilege; being unprivileged makes the under-count worse.
  - Cross-check against `top -l 2 -s 2 -stats pid,command,power` (second sample): WindowServer topped the POWER column (48.4), consistent with it also topping %CPU. However `top`'s POWER column is an "energy impact" score (same concept as Activity Monitor's Energy Impact), not literal watts, so it can't be numerically reconciled with our watts — only used for relative ranking. Ranking-wise it reinforces the same EPERM blind spot: our top visible consumer (Telegram, ~11.6 mW) is nowhere near `top`'s highest scorers, because those are either EPERM'd for us or (Telegram itself) simply billed very little CPU/GPU energy in this window.
- Disk I/O (top consumers, KB/s, cumulative `ri_diskio_bytesread + ri_diskio_byteswritten` deltas over the sample window): claude ≈ 135 KB/s, Codex (Service) ≈ 70 KB/s, Claude ≈ 4 KB/s, Claude Helper ≈ 2 KB/s, cfprefsd ≈ 2 KB/s (a separate run showed Arc ≈ 88 KB/s, claude ≈ 38 KB/s, Claude ≈ 8 KB/s — same order of magnitude, different snapshot in time). Magnitudes (tens to ~100s of KB/s) are plausible for background app cache/log writes and editor/agent-tool I/O; nothing pegged at an implausible value. No independent tool cross-check: neither `top` nor `ps` expose a per-process disk-rate column, so this is validated only by unit/dimensional analysis (`ri_diskio_*` are cumulative byte counters since process start, per Apple's `rusage_info` docs, matching how the spike deltas them).
- Grouping: responsible PID works — `responsibleFail=1` out of 592 processes in the second sample (one process, likely one that exited between samples or a system daemon with no responsible-PID mapping). Chrome/Electron-style helper processes correctly collapse into one row: Arc → `procs=41`, Discord → `procs=9`, Claude Desktop → `procs=30`, ChatGPT → `procs=25`, Docker → `procs=9`, the `claude` CLI → `procs=43`.
- Accuracy vs Activity Monitor (proxied via `top -l 2 -s 2 -o cpu -n 15 -stats pid,command,cpu,mem` second sample and `ps -Ao pid,user,%cpu,rss,comm -r | head -20`, since no GUI is available in this environment):
  - `top`/`ps` top CPU consumers this run: WindowServer (52.5%, top), PerfPowerServices (44.2%, top), Discord Helper (Renderer) (14-18%), Browser Helper/Arc (multiple, several % each), Telegram (10-11%), kernel_task (11.7%), claude CLI processes (~14-18% each in `ps`).
  - Spike's top CPU app rows: claude 106.9% (procs=43, sum of many concurrent CLI session processes — consistent with `ps` showing multiple `claude` binaries each in the low double digits), Arc 23.9% (procs=41, consistent with summing several Browser Helper renderer processes seen in `ps`), Discord 11.3% (procs=9, same order of magnitude as the single Discord Helper renderer `ps` shows), Telegram 6.6%.
  - WindowServer, PerfPowerServices, and kernel_task do NOT appear in the spike's app ranking at all — they're EPERM-denied under `proc_pid_rusage`, so their real (and here, very high) CPU cost is invisible to this API without root. This is the single biggest accuracy gap: any privileged system process's CPU/energy/memory is unobservable unprivileged.
  - Footprint (RSS proxy): spike's top footprint apps (Arc 4952 MB, Claude 2220 MB, claude 2086 MB, Docker 1739 MB, ChatGPT 1530 MB) are in the same range/order as `ps` RSS values for the corresponding processes (converted to MB), within expected slack since `ri_phys_footprint` and RSS are different metrics.
  - Given the different sampling windows/tools (spike: 2s delta between two `proc_pid_rusage` samples; `top`/`ps`: point-in-time or their own internal windows) exact percentages are not expected to match, only relative ranking and order of magnitude — that held for user-space apps.
- EPERM facts:
  - `proc_pid_rusage` returns EPERM (errno 1) for: kernel_task, launchd, WindowServer, mds_stores, and any process not owned by the calling (non-root) user — confirmed for 330/921 pids this run.
  - `proc_name()` is gated the same way: it also returns failure (errno 1 / EPERM) for those same non-owned/root pids when called unprivileged, so the spike's fallback naming (`"pid \(pid)"`) kicks in for every EPERM'd pid in the printed sample — we cannot even resolve the *name* of a denied process without elevated privileges, only its pid.
  - Could not test as root in this environment: `sudo` requires an interactive TTY/password prompt not available here, so EPERM count "as root" was not directly verified, only inferred (root should get errno=0 for all of the above based on documented `proc_pid_rusage` semantics).
- Notes / gotchas:
  - mach ticks → ns via `mach_timebase_info` — confirmed necessary; the build/run behaved correctly with this conversion (delta CPU% numbers over the 2s window landed in plausible 0-100%+ ranges, not obviously scaled off).
  - `POSIXErrorCode` does NOT conform to `Error` on this toolchain (Swift 6.3.3 / macOS 26 SDK), so `Result<Sample, POSIXErrorCode>` fails to compile with "type 'POSIXErrorCode' does not conform to protocol 'Error'". Fixed by using `Result<Sample, POSIXError>` and `POSIXError(POSIXErrorCode(rawValue: errno) ?? .EINVAL)` for construction, and matching with `case .failure(let e) where e.code == .EPERM` instead of `case .failure(.EPERM)`. See task-1-report.md for details.
  - Caveat: all deltas here (CPU, energy, disk) are computed by diffing two `proc_pid_rusage` samples keyed only on `pid_t`. This assumes the PID was not reused between samples (2s apart in this spike, but production sweeps may be slower or a short-lived process may exit/respawn faster). A production sweep must key on `pid + start time`, not `pid` alone — either `proc_bsdinfo.pbi_start_tvsec` (via `proc_pidinfo(PROC_PIDTBSDINFO)`) or `rusage_info_v4.ri_proc_start_abstime`, to detect a pid reused by a different process between samples and avoid attributing one process's counters to another.

### Symbol inventory
Every private/system API, struct, flavor constant, and field this spike touches, with units:
- `proc_listallpids(void *buffer, int buffersize) -> int` (libproc, `<libproc.h>`): enumerates all live PIDs. Return value is a **count of pids** the way this spike uses it (buffer sized as `count * MemoryLayout<pid_t>.size` bytes); no physical unit.
- `proc_pid_rusage(pid_t pid, int flavor, rusage_info_t *buffer) -> int` (libproc): fills per-process resource-usage counters for `pid`. Returns `0` on success, `-1` with `errno` set on failure (EPERM/ESRCH/…); no unit (status code).
  - `RUSAGE_INFO_V4` (`<sys/resource.h>`): integer flavor constant selecting the ABI layout `rusage_info_t` must be cast to — here, `rusage_info_v4`. No unit (enum-like tag).
  - `rusage_info_v4` struct fields used (`<sys/resource.h>`):
    - `ri_user_time` — user-mode CPU time, in **Mach absolute-time ticks** (NOT nanoseconds on Apple Silicon — requires `mach_timebase_info` conversion).
    - `ri_system_time` — kernel-mode CPU time, same unit as `ri_user_time` (Mach ticks).
    - `ri_phys_footprint` — resident/compressed memory footprint, in **bytes**.
    - `ri_diskio_bytesread` — cumulative bytes read from disk since process start, in **bytes**.
    - `ri_diskio_byteswritten` — cumulative bytes written to disk since process start, in **bytes**.
    - `ri_billed_energy` — cumulative energy billed to the task, in **nanojoules (nJ)**.
- `mach_timebase_info(mach_timebase_info_t *info) -> kern_return_t` and `mach_timebase_info_data_t{ numer, denom }` (both `uint32_t`, unitless ratio) (`<mach/mach_time.h>`): converts Mach absolute-time ticks to nanoseconds via `ticks * numer / denom`. Confirmed required on this M1 Max (ticks are not 1:1 with ns on Apple Silicon).
- `proc_pidpath(pid_t pid, void *buffer, uint32_t buffersize) -> int` (libproc): writes the process's executable path (up to `4 * MAXPATHLEN` bytes as sized here) into `buffer`; returns path length in bytes, `<= 0` on failure. Value is a string, no numeric unit.
- `proc_name(pid_t pid, void *buffer, uint32_t buffersize) -> int` (libproc): writes the short BSD process name (up to 256 bytes as sized here); returns name length in bytes, `<= 0`/EPERM on failure for pids not owned by the caller (see EPERM facts above). Value is a string, no numeric unit.
- `responsibility_get_pid_responsible_for_pid(pid_t pid) -> pid_t` (libquarantine, re-exported by libSystem; no public header, declared locally in `CPrivate/include/Responsibility.h`): maps `pid` to the pid macOS attributes its resource usage to (e.g. a Chrome/Electron helper → its parent app). Return value is a `pid_t` (an opaque process identifier, not a magnitude); `<= 0` means failure/no mapping.
